# v1.2 pilot data handling and launch review

This is an implementation/operations record, not a determination of legal compliance. The demo contains fictional identities only. Before collecting real minors' data, the operator must approve its notices, authority/consent process, retention periods and deletion procedure with the appropriate reviewers. No legal or coaching review was performed by the coding agent.

## Data and access implemented

Users contain an opaque OIDC subject, chosen display name and catalogue-admin flag; the application does not request date of birth, address, phone, medical information or player email. Teams have names, age division, season and optional organization grouping. Membership is explicit per team. A display name or identity-provider subject may still identify a person and must be treated as private.

Coaches/admins see private drafts and team completion records. Players see published assignments authorized for their own membership and their own completion. A catalogue administrator has no automatic access to private teams. Invitations store token hashes, expiry, role and use/revocation time. Expired/revoked/used links cannot be accepted. A suspended membership immediately blocks subsequent team API access. Already downloaded lesson data cannot be recalled from a user's device.

There are no public profiles, indexable lesson links, public rankings, advertisements, third-party analytics, social features or incomplete guardian login. A real guardian/consent workflow is outside the exposed capabilities and must not be implied by the existing roles. Lesson metadata is coach-authored text; coaches should avoid unnecessary personal/sensitive details.

Cookies are HttpOnly/SameSite with Secure required in production. API responses are no-store. Credentials and callback query strings are excluded from request logs. Published content uses immutable copies, so editing a draft is not an erasure of earlier lesson versions. Coach authorship and access administration are audited. TLS, private buckets, encrypted managed disks and access to hosting/backup logs remain deployment responsibilities.

## Pilot retention and deletion process to approve

Suggested operational defaults: remove expired sessions/OIDC state promptly, remove consumed/expired invitations and idempotency rows after 30 days, retain operational logs/backups on a 30-day rotation, and review team content at the end of each season. `pnpm db:prune` removes expired credentials and those old transient rows; it never deletes projects, lesson publications, members or progress. No recurring scheduler is installed. Do not silently delete content when Pro expires or a project is archived.

A deletion request must be handled by an authorized operator: verify the requester and the affected team/account scope; suspend/revoke access first; identify shared lessons and applicable preservation obligations; produce any required private export through controlled database administration; erase or pseudonymize the scoped relational records, immutable object copies and derived progress under a reviewed maintenance procedure; propagate to retained backups according to the approved rotation; record completion and exceptions without retaining unnecessary original personal data. Database version immutability intentionally prevents ordinary API edits from silently erasing published history. There is no self-service erasure endpoint in this MVP; the operator must finalize and rehearse this privileged procedure before a real-data pilot.

The implementation does not run an external consent service, a legal-retention scheduler, a parental portal or third-party identity-provider deletion. Access policies in the identity provider and existing team enrollment process must be coordinated with the application. Real device accessibility, inclusive user tests and age-appropriate lesson review remain human acceptance work.
