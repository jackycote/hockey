# Hockey Doo v1.2 — local demo and operations

A prepared local review demo is available at `http://127.0.0.1:5184/equipes` (API 3101, separate `.data/v1.2-demo` storage). Choose **Coach Démo**. [Coach preview](demo/v1.2/coach-workspace.png) · [Mobile player preview](demo/v1.2/player-mobile.png).

## Start and demonstrate

Use Node 24 and pnpm 12.21.0. From the repository root:

```sh
corepack pnpm install --frozen-lockfile
corepack pnpm setup:env
corepack pnpm demo
```

Open `http://127.0.0.1:5174/equipes`. `pnpm demo` enables synthetic sign-in, migrates local embedded PostgreSQL and seeds the demo once. Its records persist under `apps/api/.data` with the default relative `API_DATA_DIR=.data`. `pnpm dev` starts the same application without enabling synthetic authentication; configure OIDC or use the explicit demo command. Both launch API/web; stop them with Ctrl-C. The original local editor and timeline remain at `/`; `/fondation` retains the initial technical demo. Imported scenario/sequence files in that editor remain local and are independent of the private team workspace.

Synthetic identities:

| Account                  | Access                                                                          |
| ------------------------ | ------------------------------------------------------------------------------- |
| Coach Démo               | Administrator of M11 Free and M13 Pro; switch teams in the active-team selector |
| Joueur M11 / M13         | Their own team's assigned published lessons and progress                        |
| Administration catalogue | Global catalogue publication; no implicit private-team access                   |

M11 has one active project with two scenarios/sequences. A second project is blocked until the first is archived. M13 has two projects. In **Mon équipe**, the demo coach can simulate Pro, or select the retained project before downgrading. Archived projects and earlier lessons are preserved. After automatic Pro expiry, **Conserver ce projet avec Free** retains the selected project and archives the others without changing billing state. The catalogue can be viewed, simulated and assigned without creating a private project. **Créer un projet depuis ce modèle** creates a normal private, quota-counted copy of its system/scenario.

Suggested demonstration: create a fresh team, create a breakout project, save its system, edit/save a scenario, **Tester ce scénario**, play/pause/step and reposition a skater. While paused, change pressure/reaction and apply the instruction. Advance to commit it to the journal. Add text/pause/arrow/focus annotations and save the sequence. Select one or more sequences in the lesson form, order them, save/publish and assign to the whole team or selected active players. A new invitation is single use and expires after 48 hours by default. Sign out, sign in as a synthetic player, accept that code, select the new team and open the assigned lesson. Seek, change speed/focus, read its system sheet and mark completion. Players do not see another player's progress.

## Production configuration

Do not enable demo authentication in production. Serve the built Vue application and `/api` under one HTTPS origin. The API binds loopback by default; put it behind the deployment's reverse proxy and provide `API_HOST` explicitly when required. No public publishing or real payment integration is implemented.

| Variable                                                       | Meaning                                                                               |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `NODE_ENV=production`                                          | Enforces production startup checks and secure cookies                                 |
| `DATABASE_URL`                                                 | Network PostgreSQL connection string; use TLS and a least-privileged application role |
| `API_DB_MODE=postgres`                                         | Explicit network mode for nonproduction; production always selects PostgreSQL         |
| `PUBLIC_APP_URL`                                               | Exact HTTPS application origin, also used for OIDC callback                           |
| `OIDC_ISSUER`, `OIDC_CLIENT_ID`, optional `OIDC_CLIENT_SECRET` | OIDC provider; register `/api/v1/auth/callback` under the public origin               |
| `ENABLE_DEMO_AUTH=false`                                       | Required in production; true is refused                                               |
| `BLOB_BACKEND=s3`                                              | Required in production                                                                |
| `S3_ENDPOINT`, `S3_BUCKET`, `S3_REGION`                        | S3-compatible private bucket, created by the operator; endpoint HTTPS in production   |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`                     | Dedicated object credentials; local MinIO root variables are a development fallback   |
| `PROPOSED_SEASON_PRICE_CAD`                                    | Indicative display price; no charge or provider integration                           |
| `BACKUP_KEY`                                                   | Separate secret: exactly 64 hex characters, 32 random bytes                           |

Never embed these secrets in the web build. Environment files and generated backups are ignored by git. `SESSION_SECRET` from earlier setup versions is unused; opaque random session tokens are hashed in SQL. Sessions expire after eight hours. OIDC state expires after ten minutes. Configure the real provider, TLS, issuer metadata/signing keys, account recovery and device/browser login before production use. The signed provider contract tests exercise validation but do not replace a live vendor integration check.

Run `pnpm build`, deploy `apps/web/dist`, run `pnpm db:migrate` with production environment, then `pnpm --filter @hockey-iq/api start`. Do not run synthetic seeds against production. There is no public self-service administrator escalation. Provision the initial catalogue administrator through controlled database administration after confirming the intended OIDC subject.

## PostgreSQL / S3 integration

`pnpm services:up` starts the Docker PostgreSQL/MinIO definitions after `pnpm setup:env`. `pnpm test:services` uses a uniquely named disposable SQL schema and S3 bucket, checks repeated migrations, a concurrent quota race and object integrity, then removes only those test resources. CI runs it after starting the services. This command requires reachable services and the credentials in `.env`; it is separate from embedded PostgreSQL unit/API tests. Docker is unavailable in the implementation environment. A separate local PostgreSQL 16 instance passed the private API integration suite. The combined `test:services` attempt could not authenticate to the database configured in `.env` and created no resources; MinIO integration remains unverified locally. The S3 SDK adapter is tested against a local protocol fixture, including conditional writes and integrity checks.

Create the application's private bucket separately from the smoke-test bucket. Deny anonymous listing/reading and public ACLs. Do not expose database or object-storage admin consoles publicly. PostgreSQL RLS can be added as defense in depth; this MVP enforces API membership checks plus tenant foreign keys/indexes, and does not claim configured RLS.

## Backup and restoration

From the repository root, with `BACKUP_KEY` supplied through the environment/secret store:

```sh
pnpm db:backup /absolute/protected/path/hockeydoo.hockeydoo
pnpm db:restore /absolute/protected/path/hockeydoo.hockeydoo
```

Both commands select the same database/blob backend as the server, including network PostgreSQL and S3 in production. Backup creates a new file with restrictive permissions and refuses overwriting it. AES-256-GCM encryption protects a consistent relational snapshot. Domain versions include the payload needed to rebuild immutable objects. Sessions and pending OIDC states are excluded. Restore only accepts an empty, migrated database and revokes pending invitations. A failed blob write/checksum aborts the SQL transaction. Unreferenced content-addressed objects left by a rollback are harmless but require later operator garbage collection.

Keep the encryption key outside the backup destination. Proposed pilot policy: daily encrypted backups, 30-day rolling retention, separate access-controlled storage and a monthly restoration drill into an isolated environment. These are operational tasks, not an installed recurring scheduler. Backups currently have a 256 MiB input/decompression bound; larger deployments need a streamed database-native encrypted backup procedure before exceeding it. Validate restored assignments and recorded hashes before bringing a restored service online.

## Limits and diagnostics

Recordings: five minutes at 30 Hz, at most 9,001 full frozen frames. Up to 12 sequences per lesson, subject to a 64 MiB uncompressed JSON/object/request limit for the assembled lesson. A long multi-sequence lesson may hit this limit and must be shortened. Rules: 64 per system, eight conditions/actions per rule; v1.1 nested conditions have depth three/node bounds and an 8,192-evaluation budget. Zones: 32, polygons up to 16 vertices, point targets: 64. Defaults are explicit contract constraints, not a per-player charge.

Production in-process rate limits are 30 authentication or 180 other requests/minute/IP per instance, configurable through `AUTH_RATE_LIMIT` and `API_RATE_LIMIT`; development allows 5,000 to support test fixtures. Use an edge/shared limiter for several instances. Lists use `limit` (1–100) and `offset`; the client retrieves pages explicitly. Request logs contain route templates, request ID, status and duration, not cookies, bodies, callback codes or query strings. SQL audit events record membership, project/version, publication, assignment and lesson access actions. No public ranking or player analytics is exposed.

`GET /api/health` retains the original compatibility response. `GET /api/ready` checks SQL readiness and reports platform v1.2. `GET /api/openapi.json` lists routes; detailed write shapes live in the Zod contracts and API tests. Monitor error/status rates, latency, storage growth and backup freshness externally. No external monitoring service has been provisioned.

Validation commands: `pnpm check`, `pnpm test:e2e`, `pnpm test:services`, `pnpm bench:tactics`. Browser tests cover desktop Chromium, mobile Chromium and mobile WebKit. Real iOS/Android devices and coach M11–M18 trials remain an external acceptance activity. Trace DOM/canvas sampling is disabled for the sustained v1.2 playback test to avoid headless software-GPU readback stalls; action/network/source traces and explicit screenshots remain available.
